# Testing strategy
Unit: policy strict validation, workflow transitions, source/path safety, final status precedence and verifier contract, Ed25519 signatures, exact request binding, provider response parsing and failure handling.
Integration: real subprocesses in temporary Git repositories, init idempotence/conflict, three instruction adapters, command failure, missing/rejecting/unsigned verifier, security thresholds, runtime requirements, stale/tampered/replayed evidence and human approval.
CLI: help, configuration exit 2, rejection exit 1, review exit 3, dry-run no writes/commands, doctor readiness, generated CI.
Required examples: all-pass, build-fail, test-fail, missing-verifier, verifier-reject and security-threshold-fail. Example verifier evidence is explicitly test-only.
Build a wheel, install it in a separate clean virtual environment and run the installed CLI. Run pytest, ruff, mypy, Bandit and pip-audit. Post-merge GitHub Actions run [36319962778](https://github.com/himitsuomom/ai-coding-governance-platform/actions/runs/36319962778) passed the configured gates. This repository does not require external verifier evidence until the restricted Workers AI token and protected Buildkite verifier step are active. When enabled, tests require a signed report bound to the exact current request and reject a tampered, unsigned, stale, replayed or unknown-issuer report. The external CI acceptance test must show that PR-controlled commands cannot read the API token or signing key. Provider tests use mocked HTTP and do not consume quota. Implementation-agent assertions never substitute for external verifier evidence when policy requires it.
